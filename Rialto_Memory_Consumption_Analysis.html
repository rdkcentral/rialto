5. GStreamer Memory Reduction Without Impacting Performance

5.1 Problem: gst_deinit() is never called in production

// GstInitialiser.cpp
~GstInitialiser()
{
    if (m_thread.joinable()) m_thread.join();

#ifdef FREE_MEM_BEFORE_EXIT    // ← only defined in CMakeLists.txt for TEST builds!
    if (m_gstWrapper) {
        m_gstWrapper->gstDeinit();
        m_gstWrapper.reset();
    }
#endif
}

In production, the GStreamer registry (~5–8MB) and all loaded plugin type classes are never freed. This is by design (GStreamer does not fully support re-initialization), but it means the baseline is permanently inflated.

5.2 Problem: Pipeline objects survive stop()

stop() only calls gst_element_set_state(pipeline, GST_STATE_NULL). The pipeline and all its child elements remain allocated:

// Stop.cpp — execute()
m_player.changePipelineState(GST_STATE_NULL);    // Sets state only
// ↑ NO gst_object_unref, NO gst_bin_remove, NO element teardown

// termPipeline() — ONLY called from ~GstGenericPlayer
m_gstWrapper->gstObjectUnref(m_context.pipeline); // Actually frees elements
m_glibWrapper->gThreadPoolStopUnusedThreads();
malloc_trim(0);                                    // Reclaims fragmented heap

6. Short-Term Solutions (Low Risk, Immediate Deployment)

S1. Reduce maxPlaybacks to 1 — CONFIG CHANGE
Save ~8.25 MB of SHM. Set via SetConfiguration IPC from RialtoServerManager. No code change required.
Pre-requisite: Confirm no dual-video or seamless-switch use case on target platform.
S2. Add malloc_trim(0) in Stop::execute() — 1-LINE FIX
Save ~5–15 MB immediately after playback stops. Reclaims fragmented glibc heap pages.
// Stop.cpp — execute()
void Stop::execute() const
{
    ...
    m_player.changePipelineState(GST_STATE_NULL);
    ...
    RIALTO_SERVER_LOG_MIL("State change to NULL requested");
    malloc_trim(0);  // ← ADD THIS
}
Risk: Negligible. malloc_trim(0) is safe to call at any time. It only returns unused pages to the OS.
S3. Add gThreadPoolStopUnusedThreads() in Stop::execute() — 1-LINE FIX
Immediately reclaims GLib thread pool threads after stop instead of waiting for the 5s idle timeout.
Risk: Negligible. Threads will be recreated on next play() if needed.
S4. Set MALLOC_ARENA_MAX=2 — ENV VAR
Add to the RialtoServer systemd service file. Limits glibc to 2 memory arenas instead of 8×ncores.
Save ~5–10 MB from reduced fragmentation overhead.
Risk: Minor. Slight thread contention on malloc under heavy multi-threaded allocation — unlikely to be measurable for Rialto's workload.
Combined short-term saving: ~20–35 MB with zero to negligible risk. This alone should bring idle-after-playback from ~70MB down to ~40–50MB range.

7. Long-Term Solutions (Higher Impact, Requires Design Changes)

L1. Destroy pipeline on stop (aggressive teardown) — DESIGN CHANGE
Instead of keeping the GstGenericPlayer alive after stop(), destroy it immediately. The MediaPipelineServerInternal session would persist (SHM partition stays mapped), but the heavyweight GStreamer pipeline, WorkerThread, and GstDispatcherThread would be freed.

Saving: ~15–25 MB after stop
Trade-off: Next play() / load() must re-create the pipeline from scratch, adding ~50–200ms latency to tune start. Requires refactoring MediaPipelineServerInternal to support lazy GstPlayer creation.
Approach:
  • On stop(): call m_gstPlayer.reset() (triggers ~GstGenericPlayer → termPipeline() → malloc_trim(0))
  • On next load(): re-create GstGenericPlayer if null
  • WorkerThread and GstDispatcherThread die with the GstPlayer
L2. Lazy / on-demand SHM allocation — DESIGN CHANGE
Currently, SHM is allocated on switchToActive() with ALL partitions pre-sized. Instead:
  • Create memfd with size 0 on switchToActive()
  • Grow (ftruncate) when mapPartition() is called
  • Shrink (or skip) when unmapPartition() is called
Saving: ~8–16 MB when ACTIVE but idle
Trade-off: Requires removing F_SEAL_GROW | F_SEAL_SHRINK seals (security concern), or using a different allocation strategy. Client must re-mmap on resize. Complex IPC coordination.
L3. Dynamic video partition sizing — OPTIMIZATION
The 7MB video region is sized for worst-case (UHD). For HD-only playback, 3–4MB is sufficient.
  • Accept a resolution parameter in createSession()
  • Size the video partition accordingly (see code comment: "As (for now) resolution of playback is not known")
Saving: ~3–4 MB per partition for HD content
Trade-off: Requires API change. May need re-allocation on resolution change.
L4. Process recycling on INACTIVE — ARCHITECTURE
Instead of keeping the same RialtoServer process across ACTIVE→INACTIVE→ACTIVE cycles, kill and respawn it. This guarantees a clean memory state.
Saving: Full reclamation of all fragmented/leaked memory
Trade-off: ~200–500ms cold start time for new process + GStreamer re-initialization. May be acceptable if INACTIVE periods are infrequent.

8. Thread Cleanup Assessment

Are there thread leaks?

No actual thread leaks. All threads are properly joined in their respective destructors. However, thread lifetime is overly long:
ThreadIssueFix
WorkerThread Lives from createSession to destroySession. Idle during stopped state. L1: Destroy GstPlayer on stop, which joins this thread
GstDispatcherThread Polls GstBus even when pipeline is in NULL state. Wastes CPU + memory. L1: Destroy GstPlayer on stop, or stop polling when state is NULL
GstInitialiser thread Runs once but std::thread object persists (joinable). Thread is finished but stack not freed until join. Call m_thread.join() after m_isInitialised = true to free the thread stack immediately
GstCapabilities init thread Same pattern — runs once, joins only on destruction Join after initialization completes
GLib thread pool Max 2 idle threads with 5s timeout. After stop, they may persist. S3: Call gThreadPoolStopUnusedThreads() on stop
