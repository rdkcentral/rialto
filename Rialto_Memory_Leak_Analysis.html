Rialto Comprehensive Memory Leak Analysis

rialto (server) + rialto-gstreamer (client plugin) + rialto-ocdm (DRM shim)

Version v0.15.2-r17 | Commit 684b94e0 | September 2026 | Full Codebase Scope

Executive Summary

This report presents a comprehensive memory leak analysis of the entire Rialto ecosystem at version v0.15.2-r17, covering three repositories:

  • rialto — Server-side GStreamer player, worker thread tasks, GstSrc, pipeline management
  • rialto-gstreamer — Client-side GStreamer plugin (MSE sinks, pull-mode delegates, buffer parser)
  • rialto-ocdm — OpenCDM DRM shim (session lifecycle, protection metadata, active sessions)

5 memory leak findings were identified (3 HIGH, 1 MEDIUM, 1 LOW). All are pre-existing issues present across releases, not introduced by the r16→r17 change. The leaks compound on every channel change, causing steady memory growth in the RialtoServer process.

Finding #1 — WorkerThread Task Queue Not Drained on Shutdown HIGH

Repository: rialto  |  File: media/server/main/source/WorkerThread.cpp

Description

When WorkerThread::shutdown() is called during pipeline teardown (every channel change), it sets m_isTaskThreadActive = false and notifies the condition variable. The taskHandler() loop then exits. However, any tasks still queued in m_taskQueue are never executed — they are simply destroyed when the queue goes out of scope.

Root Cause Code

// WorkerThread.cpp - taskHandler()
void WorkerThread::taskHandler()
{
    while (m_isTaskThreadActive) // exits immediately on shutdown
    {
        std::unique_lock lock(m_taskMutex);
        m_cv.wait(lock, [&] { return !m_taskQueue.empty() || !m_isTaskThreadActive; });
        if (!m_isTaskThreadActive) break; // <-- remaining tasks abandoned
        auto task = std::move(m_taskQueue.front());
        m_taskQueue.pop();
        lock.unlock();
        task->execute();
    }
    // m_taskQueue destroyed here with unexecuted tasks still in it
}

Why This Leaks

Tasks like SetupElement, SetupSource, and HandleBusMessage hold referenced GStreamer objects (GstElement*, GstMessage*) that are only unreffed inside execute(). When these tasks are destroyed without execution, their destructors run but do NOT unref the GStreamer objects — causing permanent leaks.

Trigger

Every pipeline teardown / channel change. The GstDispatcherThread and GStreamer callbacks may enqueue tasks right up until the worker thread exits. Any task enqueued after the last taskHandler() iteration is leaked.

Finding #2 — SetupElement Destructor Missing gstObjectUnref HIGH

Repository: rialto  |  File: media/server/gstplayer/source/tasks/generic/SetupElement.cpp

Description

The SetupElement task takes ownership of a GstElement* (via gst_object_ref at the call site). The element is only unreffed inside execute(). The destructor does NOT unref it.

// SetupElement constructor - takes ownership of referenced GstElement*
SetupElement::SetupElement(..., GstElement *element)
    : ..., m_element{element}  // holds the ref
{ }

// Destructor - NO UNREF
SetupElement::~SetupElement()
{
    RIALTO_SERVER_LOG_DEBUG("SetupElement finished");
    // m_element is NOT unreffed here!
}

// execute() - unrefs only here
void SetupElement::execute() const
{
    // ... uses m_element ...
    m_gstWrapper->gstObjectUnref(m_element); // line ~343
}

Correct Pattern (DeepElementAdded)

// DeepElementAdded destructor - CORRECTLY unrefs
DeepElementAdded::~DeepElementAdded()
{
    m_glibWrapper->gFree(m_elementName);
    m_gstWrapper->gstObjectUnref(m_element); // Always unrefs
}

Impact

Combined with Finding #1: if a SetupElement task is in the worker queue when shutdown occurs, the GstElement* is permanently leaked. Each leaked element holds its entire sub-pipeline tree.

Finding #3 — SetupSource Destructor Missing gstObjectUnref HIGH

Repository: rialto  |  File: media/server/gstplayer/source/tasks/generic/SetupSource.cpp

Description

The SetupSource task takes ownership of a GstElement* (m_source) but does NOT unref it in either the destructor OR execute(). The source element is eventually unreffed in termPipeline(), but only if the task was executed and the source was stored in the context.

// SetupSource - no unref anywhere in the task
SetupSource::SetupSource(..., GstElement *source)
    : ..., m_source{source}  // holds the ref
{ }

SetupSource::~SetupSource()
{
    RIALTO_SERVER_LOG_DEBUG("SetupSource finished");
    // m_source NOT unreffed!
}

void SetupSource::execute() const
{
    m_context.source = m_source; // transfers to context, no unref
    // ...
}

Impact

If SetupSource is destroyed without execute() (Finding #1), the GstElement* ref is permanently leaked. The source element (rialto GstSrc) is a significant allocation holding the entire source bin.

Finding #4 — HandleBusMessage Destructor Missing gstMessageUnref MEDIUM

Repository: rialto  |  File: media/server/gstplayer/source/tasks/generic/HandleBusMessage.cpp

Description

The HandleBusMessage task takes ownership of a GstMessage* (the constructor receives an already-reffed message). The message is unreffed only inside execute(). The destructor does NOT unref it.

// Constructor - takes ownership of reffed GstMessage*
HandleBusMessage::HandleBusMessage(..., GstMessage *message, ...)
    : ..., m_message{message}
{ }

// Destructor - NO UNREF
HandleBusMessage::~HandleBusMessage()
{
    RIALTO_SERVER_LOG_DEBUG("HandleBusMessage finished");
    // m_message NOT unreffed!
}

// execute() - unrefs only here (line ~306)
void HandleBusMessage::execute() const
{
    // ... processes message ...
    m_gstWrapper->gstMessageUnref(m_message);
}

Severity Rationale

Rated MEDIUM (not HIGH) because the GstDispatcherThread is reset before the WorkerThread in the GstGenericPlayer destructor. This narrows the race window, but does not eliminate it entirely. GstMessages can carry embedded GstBuffers, GstCaps, GstStructures, and GstTagLists — all of which leak with the message.

Finding #5 — SynchroniseSubtitleClock: GstStructure Leak on Error Path LOW

Repository: rialto  |  File: media/server/gstplayer/source/tasks/generic/SynchroniseSubtitleClock.cpp

Description

In SynchroniseSubtitleClock::execute(), a GstStructure is created, then passed to gstEventNewCustom(). If the event creation fails (returns NULL), the structure is leaked because the code only logs an error and returns.

GstStructure *structure = m_gstWrapper->gstStructureNew("current-pts", ...);
GstEvent *event = m_gstWrapper->gstEventNewCustom(GST_EVENT_CUSTOM_DOWNSTREAM_OOB, structure);

if (event)
{
    // gst_element_send_event takes ownership of event (and its structure)
    m_gstWrapper->gstElementSendEvent(source, event);
}
else
{
    // ERROR: structure is leaked here!
    RIALTO_SERVER_LOG_ERROR("Failed to create current-pts event");
}

Note

Per GStreamer API: gst_event_new_custom() takes ownership of the structure on success. On failure (NULL return), ownership is NOT transferred, so the caller must free it. The same pattern exists in SetPlaybackRate.cpp but there the event creation is unlikely to fail since the pipeline is valid.

Severity Rationale

Rated LOW because gst_event_new_custom() rarely fails in practice, and the leaked structure is small. However, it is still a correctness issue.

Recommended Fixes

Fix 1: Add unref to task destructors (Findings #2, #3, #4)

// SetupElement.cpp - add to destructor:
SetupElement::~SetupElement()
{
    RIALTO_SERVER_LOG_DEBUG("SetupElement finished");
    if (m_element)
        m_gstWrapper->gstObjectUnref(m_element);
}

// SetupSource.cpp - add to destructor:
SetupSource::~SetupSource()
{
    RIALTO_SERVER_LOG_DEBUG("SetupSource finished");
    // Only unref if execute() was not called (source not transferred to context)
    // Use a flag or check m_context.source != m_source
}

// HandleBusMessage.cpp - add to destructor:
HandleBusMessage::~HandleBusMessage()
{
    RIALTO_SERVER_LOG_DEBUG("HandleBusMessage finished");
    if (m_message)
        m_gstWrapper->gstMessageUnref(m_message);
}
// Also: set m_message = nullptr after unref in execute()

Fix 2: Drain task queue on WorkerThread shutdown (Finding #1)

// WorkerThread.cpp - after taskHandler loop exits:
void WorkerThread::taskHandler()
{
    while (m_isTaskThreadActive) { /* ... existing loop ... */ }

    // Drain remaining tasks so their destructors run
    // (destructors must unref their GStreamer objects per Fix 1)
    std::lock_guard lock(m_taskMutex);
    while (!m_taskQueue.empty())
    {
        m_taskQueue.pop(); // destructor runs, unrefs resources
    }
}

Fix 3: Free GstStructure on event creation failure (Finding #5)

// SynchroniseSubtitleClock.cpp:
GstEvent *event = m_gstWrapper->gstEventNewCustom(GST_EVENT_CUSTOM_DOWNSTREAM_OOB, structure);
if (!event)
{
    m_gstWrapper->gstStructureFree(structure); // prevent leak
    RIALTO_SERVER_LOG_ERROR("Failed to create current-pts event");
    return;
}

Key Observation: v0.15.2-r17 Change Does NOT Introduce Leaks

The single-line change in r17 (adding m_context.audioSourceRemoved condition to reattachSource()) was verified and does not introduce any new memory leak. All GstCaps objects on all code paths are properly unreffed. The memory leak issues identified in this report are pre-existing across all previous releases.
